# INC-20261112-009 — Engine stop settings and SES behaviour measured on this host (Freerouting 2.1.0 / Java 23)

**Date:** 2026-11-12 00:30-01:10 local. **Terminal:** DESK development (read-only toward the live WATCH board; all runs on scratch copies in `%TEMP%`). **Related:** KF-20261111-006, LSN-20261111-004 items B/C.

## What was tried (measured, not guessed)

| Run | Setup | Result |
|---|---|---|
| A/B 1 | scratch copy of the WATCH tuned DSN, new orchestrator, 240 s budget, per-run `freerouting.json` with nested `autorouter.*`/`plane_nets`, merged into `%TEMP%\freerouting\freerouting.json` | 21 passes in 360 s, unrouted 68 → best 8 (pass 16); engine ignored the 4-minute `job_timeout`; killed at budget + 120 s; **no SES** |

## Findings

1. Freerouting 2.1.0 on this host ignores `job_timeout` and `max_passes` in both the per-run and the global `freerouting.json` and on the CLI. It runs until 100 % or until killed. This matches attempts 5-7 in LSN-20261111-004.
2. The SES write path works on this host: when the engine completes, `-do` is written. So "no SES" on WATCH is not an I/O or permissions problem; it is the engine never completing and DESK having no way to make 2.1.0 stop gracefully.
3. The 2.2.4 / 2.4.1 / 2.5.0 JARs in `library/tools` are compiled for Java 25 (class file 69); the installed OpenJDK 23 cannot load them. Those versions honour `max_passes`, have `stagnation_pass_limit`, score by completion and restore the best board (Freerouting docs, releases v2.2.4 and v2.5.0).
4. Downloading a JDK from inside the DESK development terminal was blocked by the sandbox policy (external binary). The install is a human step.

## What DESK now does

- `RoutingEngineOrchestrator.smoke_test()` runs the tiny fixture before any long run; a run with no SES is reported as `SMOKE_NO_SES` and `tools/route.py` stops instead of starting a 15-minute job.
- `find_java()` prefers `DESK_JAVA`, then a JDK under `library/tools/jdk*/bin`, then PATH; discovery picks the highest Freerouting version the chosen Java can load; `desk doctor` reports a Java < 25 as a WARN with the install instruction.
- `PassTracker` stops on "no new best for N passes"; `progress.json` carries pass history, best pass and problem nets by name (pin ids mapped through the DSN network block).
- Pre-flight gate refuses boards whose DSN lacks declared planes, whose outline is not one closed primitive, or whose pads sit inside routing keep-outs.

## Still open

- Proof that a *stopped* long job returns a SES requires Freerouting ≥ 2.2, i.e. Java 25. Install step: unzip a Temurin JDK 25 (Windows x64) into `library/tools/jdk25/` (git-ignored) or set `DESK_JAVA` to its `bin\java.exe`; then run `python desk.py doctor` (expects Freerouting v2.5.0) and re-run the A/B on the scratch DSN; record the result here.
- Windows has no graceful-stop signal for a child JVM; with 2.1.0 the only bounded, SES-producing paths are 100 % completion or EasyEDA's native autorouter.

## Resolution 2026-11-12 01:10 — Java 25 installed, proof obtained

The Founder unpacked Temurin JDK 25.0.5+8 into `library/tools/jdk25/` (git-ignored). `desk doctor` now reports the bundled Java and selects `freerouting-2.5.0.jar`.

| Run (Freerouting 2.5.0, bundled JDK) | Result |
|---|---|
| Smoke fixture, `-mp 2` | SES in 4.4 s |
| Scratch WATCH DSN, `--router.autorouter.max_passes=6`, 240 s budget, `via_costs 80` | **stopped by itself after 6 passes in 138 s and wrote a 100,966-byte SES**; unrouted 42 → 25 → 17 → 13 → 12 → 11; 48 clearance violations present from the baseline board; `rc 0`, status SUCCESS |

So the "no SES" failure is closed: with 2.5.0 the engine honours `max_passes` (and `job_timeout`), scores by completion, and writes its best board at the end. Notes: 2.5.0 rejects `router.autorouter.stagnation_pass_limit` ("No field found"), so DESK's `PassTracker` remains the plateau stop and the flag is opt-in (`DESK_FR_STAGNATION_FLAG=1`); the per-pass log format changed ("with score X (N unrouted and M violations)") and the parser now reads it, including the violation count. Pass 1 on 2.5.0 started at 42 unrouted where 2.1.0 started at 64-68 on the same DSN.

Open: `PhysicalConnectivityVerifier` on this SES against the live dump reports 27/60 nets fully connected (45 %) while the engine reports 11 unrouted connections of 257; the coordinate frame was verified as identical (track endpoints land on same-net pads), so the remaining gap is a verifier/parser question (QA-03), not an engine one. The SES was not imported into any live board.
