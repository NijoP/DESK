## Findings

1. Freerouting 2.1.0 on this host ignores `job_timeout` and `max_passes` in both the per-run and the global `freerouting.json` and on the CLI. It runs until 100 % or until killed. This matches attempts 5-7 in LSN-20261111-004.
2. The SES write path works on this host: when the engine completes, `-do` is written. So "no SES" on WATCH is not an I/O or permissions problem; it is the engine never completing and DESK having no way to make 2.1.0 stop gracefully.
3. The 2.2.4 / 2.4.1 / 2.5.0 JARs in `library/tools` are compiled for Java 25 (class file 69); the installed OpenJDK 23 cannot load them. Those versions honour `max_passes`, have `stagnation_pass_limit`, score by completion and restore the best board (Freerouting docs, releases v2.2.4 and v2.5.0).
4. Downloading a JDK from inside the DESK development terminal was blocked by the sandbox policy (external binary). The install is a human step.

## What DESK now does

- `RoutingEngineOrchestrator.smoke_test()` runs the tiny fixture before any long run; a run with no SES is reported as `SMOKE_NO_SES` and `tools/route.py` stops instead of starting a 15-minute job.
- `find_java()` prefers `DESK_JAVA`, then a JDK under `library/tools/jdk*/bin`, then PATH; discovery picks the highest Freerouting version the chosen Java can load; `desk doctor` reports a Java < 25 as a WARN with the install instruction.
- `PassTracker` stops on "no new best for N passes"; `progress.json` carries pass history, best pass and problem nets by name (pin ids mapped through the DSN network block).
- Pre-flight gate refuses boards whose DSN lacks declared planes, whose outline is not one closed primitive, or whose pads sit inside routing keep-outs.

## Still open

Install step: unzip a Temurin JDK 25 (Windows x64) into `library/tools/jdk25/` (git-ignored) or set `DESK_JAVA` to its `bin\java.exe`; then run `python desk.py doctor` (expects Freerouting v2.5.0) and re-run the A/B on the scratch DSN; record the result here.

## QA-03 resolved 2026-11-12 01:50 — verifier agrees with the engine after two geometry fixes

Root causes of the 45 % verdict on a board the engine reported as 96 % connected:
1. **Pad size.** `PhysicalConnectivityVerifier` and `BoardIntelligenceEngine` read pad width/height from keys (`w`/`h`) the EasyEDA dump does not carry and fell back to 15 mil for every pad; real pads are 30-40 mil, so track endpoints landing on a pad edge were "not touching". Fixed: `pad_size_mil()` reads `shape: [kind, w, h, ...]`.
2. **Double rotation.** `tools/pcb_dump.py` stores pad offsets as `pad.getState_X() - component.x`, i.e. already in the board frame. `routability.py`, `routing/board.py`, `routing/connectivity.py`, `snapshot.py`, `placement_refine.py`, `preflight.py` and `tools/pcb_place.py` rotated those offsets again by the component rotation, mislocating every pad of the 36 rotated parts on WATCH. Measured: 405/1130 SES track endpoints land on their pads with the offsets used as-is versus 324 with the extra rotation. Fixed: `pad_xy()` applies only a rotation *delta* to a planned orientation; the SES inner layers now map to EasyEDA ids 15/16.

Result on the same 2.5.0 SES against the live dump with declared planes: **51/60 nets fully connected, 15 unconnected pads of 320**, versus the engine's 11 open connections. Remaining open nets (GND ×2 pads, I2S_MIC_WS, I2S_MIC_SD1/SD2, NET_BST_FB, I2C_SCL, SPK_P, NET_ITERM, LED_4) are the engine's own unrouted set. Regression test: `tests/test_pad_frame.py`.

Side effect: the dense-board scores changed (real pad sizes block more of each cell); WATCH now reads congestion 0.98 with 43 overloaded cells and 23 regions, top cause "keep-out or pad crossing (detour required)". The benchmark tables were regenerated.

## 2026-11-12 02:15 — plateau stop on Windows loses the SES even with 2.5.0

Scratch WATCH DSN, 2.5.0, `max_passes 40`, budget 600 s, DESK patience 8, density priority classes and plane nets: unrouted 42 → **4 at pass 9** (passes 10-17 oscillated 4-7). DESK declared a plateau at pass 17 and called `terminate()`; the JVM died before writing the SES (`STAGNATED, ses=False`). The engine writes its output only when the job ends on its own (max_passes / job_timeout), and Windows offers no graceful stop for a child JVM.

Consequence: DESK must never terminate the engine on Windows when it wants a result. The bounded, SES-producing pattern is **chunked execution**: run `max_passes = N` chunks that end naturally, keep the best SES, and continue from it with `-de board.dsn+best.ses` until no chunk improves. Continuation behaviour under test next.
