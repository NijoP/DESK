# INC-20251111-001

## Metadata
- **Date/Time:** 2025-11-11 14:30 UTC
- **Project/Task:** 6-up Sensor PCB Panelisation (DESK panelisation engine development)
- **Subsystem:** easyeda-integration / pcb-panelisation
- **Severity:** HIGH
- **Status:** RECOVERED

---

## Context
**What were you trying to accomplish?**
Building DESK's panelisation engine to create a 6-up manufacturing panel (2 columns × 3 rows) from a completed sensor PCB in EasyEDA Pro. The first step was extracting the master PCB geometry (components, tracks, vias, copper zones, board outline, nets) via the EasyEDA API bridge.

---

## Expected Behaviour
**What should have happened?**
A single bridge execution call should return all PCB primitive data needed for panel generation, including components with pad details, tracks, vias, copper pour zones, poured regions, board outline, and net names.

---

## Actual Behaviour
**What actually happened?**
The monolithic JavaScript extraction script (500+ lines) caused a **500 Internal Server Error** with "a is not iterable" when executed via the bridge. The error occurred in `eda.pcb_Document.getPrimitivesInRegion()` or when processing the returned data.

---

## Error Evidence
```
HTTP 500: {"success":false,"error":"a is not iterable"}
```

The error was non-deterministic - sometimes the same script worked, sometimes it failed.

**Script structure that failed:**
- Single large async function doing 8 sequential API calls
- Used `getAll()` methods on multiple primitive types
- Complex polygon processing for board outline
- Large return object with nested arrays

---

## Root Cause Analysis

### Identified Cause
**Bridge execution timeout / memory limit exceeded** when processing large monolithic scripts. The EasyEDA bridge has an implicit execution time or memory limit that causes non-deterministic failures when scripts exceed complexity thresholds.

### Classification
- [x] Incorrect assumption (assumed single large script would work reliably)
- [ ] Missing documentation
- [ ] API incompatibility
- [ ] Implementation defect
- [ ] Engineering mistake
- [ ] Validation failure
- [ ] Environmental problem
- [x] Resource/performance limitation
- [ ] Unknown cause

### Why the Original Approach Failed
The monolithic script attempted to:
1. Open document
2. Get all component IDs → get all components → get all pads for each component
3. Get all tracks (lines)
4. Get all vias
5. Get all copper pours
6. Get all poured regions
7. Get all regions (for board outline)
8. Get all net names

Each `getAll()` call returns arrays that must be iterated in JavaScript. The combined data volume (466 lines, 22 components × ~8 pads each, 44 vias, 5 regions) exceeded the bridge's processing capacity in a single execution context.

---

## Recovery

### Attempts Made
| Attempt | Action | Result |
|---------|--------|--------|
| 1 | Execute full monolithic script | FAILED (500 error) |
| 2 | Retry same script | PARTIAL (intermittent success) |
| 3 | Split into 8 smaller sequential calls | SUCCESS |

### Successful Solution
**Decompose extraction into 8 independent bridge calls**, each with focused scope:
1. `open_document` - ensure correct PCB is active
2. `extract_components` - components + pads only
3. `extract_tracks` - lines only
4. `extract_vias` - vias only
5. `extract_zones` - copper pours only
6. `extract_poured_regions` - poured regions only
7. `extract_outline` - board outline region only
8. `extract_nets` - net names only

Each call executes in <15 seconds and returns <5KB JSON.

### Verification Evidence
All 8 calls succeeded consistently:
- Components: 22 extracted with full pad data
- Tracks: 466 lines extracted
- Vias: 44 extracted
- Zones: 4 copper pours extracted
- Poured regions: 4 extracted
- Outline: rectangle polygon extracted
- Nets: 20 net names extracted

---

## Engineering Learning

### What This Failure Taught You
Bridge execution environments have hidden resource limits. Monolithic scripts that work in browser console fail in the bridge server due to different execution contexts (V8 isolates, memory limits, timeout policies).

### Why Original Approach Failed
Assumed the bridge was equivalent to browser console execution. It is not - it's a constrained server-side environment.

### What Should Have Been Done Differently
Start with smallest possible API calls. Validate each primitive type independently before composing.

### Missing Information
Bridge server resource limits (timeout, memory, payload size) are undocumented.

### Early Warning Signs
- Script >200 lines
- Multiple `getAll()` + `map()` operations
- Return payload >10KB

### Future Prevention
**Rule:** Never execute monolithic scripts >100 lines via bridge. Decompose into atomic operations.

---

## Prevention Strategy

### Preventive Rule/Procedure
```
BRIDGE_SCRIPT_RULES:
1. Max 100 lines per bridge execution
2. Single API domain per call (components OR tracks OR vias, not all)
3. Max 5KB return payload
4. 15s timeout per call
5. Validate each primitive type independently before composition
```

### Implementation in DESK
Updated `PanelisationEngine.extract_pcb_geometry()` to use 8 separate `bridge_executor` calls instead of 1 monolithic script.
