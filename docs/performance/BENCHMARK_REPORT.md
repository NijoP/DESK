# DESK performance benchmark report (roadmap I-10)

**Status:** software-tested with a synthetic fixture; not validated on a live design. Every number in this report was
measured by the `perf` job of `.github/workflows/ci.yml` on GitHub-hosted runners. No number was estimated or taken
from a developer laptop.

- **Run:** https://github.com/NijoP/DESK/actions/runs/44908335287 (PR https://github.com/NijoP/DESK/pull/16, commit `ce0ddc6`).
- **Raw data:** the `perf-Linux`, `perf-Windows` and `perf-macOS` artifacts of that run (JSON, schema `desk.perf.offline/1`).
- **Reproduce:** `python tools/profile_perf.py --offline --scale 1,4,16 --repeat 7`.

## What was measured

- **Input:** `tests/fixtures/perf/synth_board.json`, a deterministic synthetic board generated by
  `desk/perf_bench.py::generate_fixture()`. It has 41 components, 162 pads and 49 nets: an MCU (QFN-48), LDO, sensor,
  SPI flash, USB-C, a programming header, a crystal and 30 passives. That is WATCH-sized; the git-ignored WATCH dump
  had 42 parts and 180 pins.
- **Scaling:** `x4` and `x16` tile the board 4 and 16 times. Signal nets are copied per tile; GND, 3V3 and VBUS stay
  shared, so those nets get large the way power nets do on a multi-block board.
- **Stages:** the 13 stages of `tools/profile_perf.py` that do real DESK work, run in pipeline order.
- **Method:** each scale runs in a fresh process. One cold pass, then 7 warm passes with tracemalloc off, which give
  the median, minimum and maximum per stage. Then one pass with tracemalloc on, which gives the peak Python allocation
  per stage. Peak RSS is the process high-water mark (`ru_maxrss` on Linux and macOS, `PeakWorkingSetSize` on Windows).
- **Not measured:** these stages need EasyEDA or Freerouting and were neither run nor timed.
  - `01_bridge_discovery`, `02_bridge_connection_establishment`, `03_window_document_verification`: need the live bridge.
  - `14_freerouting_execution`: external Java process.
  - `16_drc_execution`: EasyEDA's own DRC.
  - `09_ratsnest_crossing_analysis` has no separate call; `build_connectivity_graph` computes it inside `08_mst_computation`.

  The existing `profile_perf.py projects/<P>` mode timed the bridge, Freerouting and DRC stages as empty `pass` blocks.
  Its numbers for those stages are not measurements.

### Cold start and growth

| | Linux | Windows | macOS |
|---|---:|---:|---:|

| Stage | x1 -> x16 time ratio (Linux / Windows / macOS) |
|---|---|
| `11_placement_validation` | 30.9x / 35.8x / 42.9x |
| `10_placement_generation` | 37.8x / 38.9x / 40.1x |
| `15_ses_import_and_parse` | 15.6x / 15.5x / 13.5x |
| `08_mst_computation` | 56.9x / 65.3x / 81.8x |
| `13_dsn_tuning` | 3.4x / 3.5x / 3.3x |
| `06_footprint_invariant_validation` | 17.1x / 15.1x / 15.1x |

The growth ratios compare a board 16 times larger (16x components and pads).
- **Close to linear:** SES parsing (13.5–15.6x) and footprint invariants (15.1–17.1x).
- **Sub-linear:** DSN tuning (3.3–3.5x). Its input is the DSN, which `tiny_board_dsn` sizes by net count.
- **Super-linear:** placement validation (31–43x), placement generation (38–40x) and above all MST (57–82x).

Ranked by the Linux median. At x4 and x16, the five slowest stages are the same on all three OSes. Windows and macOS

each other. Persistence is a file append and read in the temp directory, so it reflects runner disk latency, not computation.

## The "sub-10 ms" claim in AGENTS.md

AGENTS.md said: "Core placement and routing evaluations must execute under 10ms." The measurements give:

- **Confirmed for each stage at WATCH size.** At x1, every stage's median is under 10 ms on all three OSes. The largest
  is placement validation: 3.8–5.4 ms.
- **Not true for the pipeline as a whole.** The sum of the 13 stage medians at x1 is 11.3–12.9 ms. A cold first pass
  is 14.5–27.5 ms.
- **Not true for larger boards.** At x4 (164 parts), placement validation is 23.8–25.9 ms. At x16 (656 parts),
  placement validation (164–181 ms), MST (81–94 ms), placement generation (53–69 ms) and SES parsing (20–26 ms) all
  exceed 10 ms.

AGENTS.md now states this scope and points here. The 10 ms figure is not a gate. Nothing in CI enforces it, and the
perf job is informational.

## Memory

- **Peak RSS** for a whole offline run, interpreter included: 24.7–29.2 MB at x1, 27.9–32.4 MB at x4 and
  43.5–47.9 MB at x16.
- **Largest peak Python allocation** in one stage at x16: 3.2 MB (SES parse) and 2.8 MB (placement validation).
- **Cold engine import** in a fresh process: 69–123 ms and 23–27 MB.

On an 8 GB machine, the DESK engines are not where memory goes. The live run in the README recorded about 11–12 GB of
EasyEDA private memory. See `LOW_SPEC_8GB_PROFILE.md`.

## Rust evaluation (D-3): migrate nothing

No Rust was written and nothing was migrated. For each hotspot, this asks whether a native rewrite could plausibly pay,
and what measurement would justify one.

| Hotspot | Algorithm (from the code) | Could native code pay? | What would justify a rewrite |
|---|---|---|---|
| `11_placement_validation` (`desk/placement.py` `check`) | Grid buckets for pad/body pair candidates, then Python per-pair geometry; growth 31–43x for 16x parts | Not at measured sizes. 167–181 ms at 656 parts runs once per placement iteration, next to EasyEDA round-trips. A native port could cut the per-pair constant, but the super-linear growth points to the candidate-pair count, which an algorithmic fix addresses first. | A real board (not this fixture) where `check` takes > 1 s per call, or > 10 % of a measured placement-loop wall time, after the pair-candidate pruning has been profiled and tightened in Python. |
| `08_mst_computation` (`desk/routability.py` `_compute_fast_mst`) | Exact Prim on a dense distance table, O(V²) per net; shared GND/3V3 grow with the board, hence 57–82x | Native code would give a constant-factor speed-up. O(V²) stays O(V²). A Euclidean MST from a Delaunay triangulation or grid neighbours is O(V log V) in pure Python, and is the first step. | A net with > ~2,000 endpoints in a real design, or MST time > 10 % of a measured routing-preflight wall time, after an O(V log V) Python version has been measured. |
| `10_placement_generation` (`desk/placement_intel.py`) | Hierarchical cluster placement in Python; growth 38–40x | Not shown. 53–69 ms at 656 parts is far below a single Freerouting pass or an EasyEDA import. | Generation > 1 s on a real board, or used inside an inner optimisation loop with many iterations per run, measured end to end. |
| `15_ses_import_and_parse` (`desk/routing/connectivity.py` `SESParser` over `SExprParser`) | S-expression tokenising and parsing; close to linear (13.5–15.6x) | Least likely of the four. Linear, 20–26 ms at 2,592 pads, and run once per routing result. A native tokenizer would save milliseconds per import. | SES files of tens of MB from real runs where parsing exceeds 1 s, or 5 % of a routing round, measured with Freerouting included. |
| `13_dsn_tuning`, `06_footprint_invariant_validation`, the rest | Linear or smaller; ≤ 9 ms at x16 | No. | None at these sizes. |

**Conclusion:** the largest DESK stage measured is under 0.2 s on a 656-part synthetic board. The external costs that
dominate a real run (EasyEDA memory, the Freerouting Java process, the human at Import Changes) are outside Python.
A Rust toolchain would add a build dependency on all three OSes for a saving that has not been shown. Revisit D-3 only
when a measurement from the table above, taken on a real design, crosses its threshold.

## Limits of this report

- **Synthetic input.** The fixture is synthetic, and a real board's net topology differs. The fixture is
  WATCH-sized, not WATCH itself.
- **Hosted runners.** GitHub-hosted runners are shared VMs. The spread between minimum and maximum is in the JSON, and
  the macOS spread at x16 is wide (for example 118–217 ms for placement validation).
- **No regression gate yet.** The I-10 acceptance item "no regression above an agreed threshold between CI runs"
  needs a threshold the Captain has not set. The job records but does not compare.
