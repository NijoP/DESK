# 01 — The mental model

> **A schematic is data first, drawing second.**
> The design lives in small JSON block specs. EasyEDA is only the renderer and the source of the netlist.
> The drawing is generated by one fixed routine, so it is always neat; the netlist proves it is correct.

## The five beliefs behind every DESK decision

1. **The netlist is the truth, the picture is a convenience.**
   A wire that *looks* connected can be open; two labels that *look* separate can merge. Only `tools/verify.py`
   (live netlist vs spec) decides if a block is done. Eyes only check neatness.

2. **Neatness is produced by rules, not by taste.**
   Every block is drawn by the same code (`desk/draw.py`): titled frame, ICs in one row, passives in a grid,
   a real wire stub + net label on every pin, alternating stub lengths, fixed fonts, 100-mil grid.
   A model never "draws" — it only fills in the spec. That is why a small model produces the same sheet as a large one.

3. **Engineering happens before drawing.**
   Every value (divider, current limit, cap rating, pull-up, threshold) is calculated from the datasheet and
   written into the block's `qa` list with `pass: true` **before** the block is built. Drawing un-validated values
   is just discovering errors later. Capture is a transcription of an already-correct design.

4. **One block at a time, finished completely.**
   `spec -> QA -> lint -> build -> verify -> accept -> save revision`, then the next block.
   Never two blocks half-done. Never two writers on the live project.

5. **Everything is decided; nothing is "fix later".**
   Every pin of every part is either on a net or explicitly in `nc`. Every part is a real library device
   (resolved MPN/LCSC). Every reset-time level is known (what is ON when the MCU is still in reset?).

## How a product is decomposed

```
Product requirements (REQUIREMENTS.md)        frozen numbers, interfaces, power budget, GPIO map
   └─ Boards                                  main board, daughter boards, ...
       └─ Subsystem blocks (BLOCK_PLAN.md)    one function each: "3V3 REGULATOR", "USB-C INPUT", "MCU CORE"
           └─ Parts                           ICs + every passive that serves them
               └─ Pins -> nets                the only thing that is electrically real
```

A good block:
- has **one function** you can say in a short UPPER-CASE title (it becomes the frame title);
- contains its IC(s) **and all their passives** (decoupling, dividers, pull-ups, filters, ESD of that interface);
- talks to other blocks **only through named ports** (nets listed in `ports`);
- is 3–25 parts. Bigger → split (e.g. `CHARGER` and `BOOST 5V` instead of `POWER`).

Typical block set for a product: `USB-C INPUT` · `BATTERY + CHARGER` · `3V3 REGULATOR` · `5V BOOST` · `MCU CORE`
· `PROGRAMMING / DEBUG` · `SENSORS` · `CONNECTORS + ESD` · `DISPLAY` · `STATUS LEDS` · `BUTTONS`.

## Order of work

0. Gate R (requirements understood, docs/00) and gate B (BOM selected incl. passives, docs/00b).
1. Blocks whose inputs are fully decided (power, MCU core) first.
2. Close open decisions (TBD in REQUIREMENTS.md).
3. Then dependent blocks (connectors, interfaces, variants).
4. Whole-sheet `verify.py all` + `lint.py --final` → 0 single-pin nets, 0 unexpected nets.
5. Only then PCB: placement (docs/04) → routing (docs/05).

## Net naming = the API between blocks

- UPPER_CASE, no spaces: `+3V3`, `VBUS`, `GND`, `USB_DP`, `I2C_SCL`, `CHG_STAT_N`.
- Active-low ends in `_N`. Power rails start with `+` or `V`.
- Internal block nets are prefixed by function: `FB_3V3`, `L_3V3_SW`, `BQ_ISET`.
- One table of global nets in `BLOCK_PLAN.md`. Reuse names; never create a synonym (`3V3` vs `+3V3` is a bug).

## Fail-safe thinking (part of "correct")

For every switch, regulator enable, GPIO-driven load and output-enable, ask: **what happens at power-up, before firmware runs?**
- Default OFF: pull-downs on active-high enables, pull-ups on active-low `OE_N`/`EN_N`.
- Check the active level of every EN pin in the datasheet (a "-1" vs "-2" suffix often flips it).
- Strapping pins of the MCU: list their required boot level and make sure nothing on the net fights it.
- Series resistors on lines leaving the board; ESD on every connector pin.
Write these as `decisions` in the block spec.
